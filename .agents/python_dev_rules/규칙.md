# ChatToCodex Development Rules

## Non-negotiable invariants

- Canonical authority is the local `project_id` plus normalized project root. ChatGPT project/chat metadata is a browser adapter binding only.
- Durable MVP state is filesystem JSON using existing atomic replacement, revision/CAS checks, and consistent cross-process file locking.
- Capacity policy is always `Reuse > Wake > Spawn`.
- Browser tab creation/reopen is explicit backend-admitted, global single-flight, and separated by 10 to 15 seconds.
- Provider rate-limit recovery uses bounded 30/60/120-second backoff.
- Polling, service-worker startup, duplicate events, and stale browser state never independently authorize a tab open.
- State updater callbacks are pure. External side effects occur after releasing locks and are finalized only after state/revision revalidation.
- Terminal and replay-defense histories are bounded while live and in-flight records are retained.
- Chrome code rechecks current tab identity, active/pinned state, wake revision, and composer ownership before acting; human input wins.
- Node harness execution is mandatory in the full test gate.
- Public async network APIs use native `asyncio` I/O rather than thread/executor wrappers around synchronous sockets. Cancellation and timeout after possible submission never imply authoritative rejection.

## Change and verification contract

- Preserve all pre-existing dirty worktree changes. Never reset, clean, or overwrite unrelated work.
- Prefer shared-boundary fixes, deletion, and existing abstractions; add no dependency without explicit request.
- Run focused regression tests, then `make ci` for Ruff format/lint, Pyrefly, Node harness availability, and pytest.
- Do not claim live browser E2E unless it was actually exercised.
- Do not commit or push without an explicit user request.
